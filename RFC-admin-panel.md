# RFC: панель управления каталогом и продажами Signal Store

## Контекст и задача

В исходном WebMCP-демо каталог из шести товаров был зашит в React-модуль, а оформление заказа не меняло состояние магазина. Для следующей статьи о встроенном агенте нужен существующий рабочий сценарий управления магазином, с которым агент сможет взаимодействовать позднее. Создаём отдельную страницу оператора и один источник данных для витрины, продаж и панели.

## Цели и границы

- На `/admin` показать все товары: название, ID, категорию, цену и остаток, а также количество товаров и единиц на складе.
- Фильтровать каталог по тексту (включая ID и характеристики), категории, наличию и диапазону цены; фильтры можно сочетать и сбрасывать.
- Создавать и удалять товары, редактировать их поля: название, категорию, цену, остаток, цвет карточки, метку, описание, характеристики. ID задаётся при создании и остаётся стабильным для корзины и истории.
- Во вкладке «Продажи» просматривать продажи, дату, состав с количеством и ценой на момент продажи, сумму продажи и суммарную выручку; фильтровать список по товару.
- Витрина и WebMCP читают тот же каталог; оформление демо-продажи фиксирует заказ и списывает остаток единым действием на сервере.
- Сохранить React + Vite и существующие три WebMCP-инструмента. Добавить бэкенд на ASP.NET Core 8 с Entity Framework Core и in-memory SQLite.

Авторизация, платежи, доставка, возвраты, роли, публичное развёртывание и встроенный агент **не входят** в эту итерацию. Заказы здесь — записи демонстрационных продаж, а не реальные покупки. Страница и API без авторизации предназначены только для локального стенда.

## Решение

В dev-режиме Vite обслуживает React SPA и проксирует `/api` на .NET-сервер `127.0.0.1:5080`; `/admin` использует тот же frontend и отдельный экран без смены стека. Прямой доступ к API также ограничен loopback-адресом. Фронтенд запрашивает данные через `src/api.js`, не хранит копию каталога в исходниках. Панель опрашивает API при открытии, витрина загружает каталог при открытии страницы; после изменения или покупки данные повторно запрашиваются. Для просмотра изменений между уже открытыми вкладками требуется обновить страницу.

Хранилище — реляционная SQL-база SQLite в памяти процесса: Entity Framework Core создаёт схему и начальные данные при старте приложения. База существует только пока работает API и при каждом новом запуске создаётся заново, поэтому отдельный файл данных, миграции и настройка пути не нужны. В начальных данных должны быть ровно **40 товаров** и **50 продаж**: каждая продажа ссылается на существующий товар, а остатки после генерации неотрицательны. Генератор должен быть детерминированным, чтобы тесты и демонстрация показывали воспроизводимые данные. История хранит снимок названия и цены позиции: удаление товара из каталога не удаляет прошлые продажи. Контекст базы живёт в одном процессе API; для демонстрационного локального стенда этого достаточно.

### Контракт API

| Метод и путь | Результат |
| --- | --- |
| `GET /api/products` | Весь каталог, включая товары с нулевым остатком. Фильтрация — на странице. |
| `POST /api/products` | Создать товар; `201`, `400` при ошибке данных, `409` при совпадении ID. |
| `PUT /api/products/{id}` | Полностью заменить товар; ID в URL и теле должны совпадать. `200`, `400` или `404`. |
| `DELETE /api/products/{id}` | Удалить из каталога; `204` или `404`. |
| `GET /api/sales?productId={id}` | Продажи от новых к старым; необязательный `productId` оставляет только продажи, содержащие выбранный товар. Неизвестный ID возвращает пустой список. |
| `POST /api/sales` | Тело `{ "items": [{ "productId": "orbit-buds", "quantity": 1 }] }`; `201` со снимком продажи, `400` при неверном запросе, `409` при недостаточном остатке, дубле позиции или отсутствии товара. |

Модель товара: `id`, `name`, `category`, `price` (целые рубли), `stock` (штуки), `accent` (HEX), `mark`, `description`, `tags` (массив строк). Сервер проверяет категорию, допустимые диапазоны и формат полей, повторные ID. Цена и остатки берутся из каталога на сервере; клиент не передаёт их при продаже. Сервер проверяет **все** позиции до списания, поэтому неуспешная продажа не меняет остатки и историю. Продажа имеет `id`, `createdAt` (UTC), `items` со снимком товара и `total`. Для фильтра на вкладке «Продажи» UI получает доступные товары из каталога, показывает выпадающий список «Все товары» и передаёт выбранный `productId` в `GET /api/sales`.

## Пользовательские сценарии и критерии приёмки

1. После каждого запуска API в каталоге ровно 40 товаров, в истории ровно 50 продаж; у всех позиций продаж существуют товары, а остатки товаров неотрицательны.
2. Открыть `/admin`, найти нужный товар по тексту, сузить список категорией, наличием и ценой. Увидеть цену и остаток даже у отсутствующего на складе товара.
3. Добавить товар со всеми полями; он появится на витрине после загрузки страницы. Изменить его цену и остаток — витрина покажет новые значения. Удалить товар — он исчезнет из каталога. После перезапуска API данные возвращаются к начальному набору из 40 товаров и 50 продаж.
4. На вкладке «Продажи» увидеть все 50 начальных продаж, выбрать товар в фильтре и увидеть только продажи с этим товаром; сброс фильтра возвращает полный список.
5. Купить на витрине доступный товар: появится запись на вкладке «Продажи» с количеством, суммой и датой, остаток уменьшится. Попытка купить больше доступного вернёт ошибку без частичной записи.
6. Удалить ранее проданный товар: продажа останется видимой с исходной ценой и названием. WebMCP `search_products`, `show_product`, `add_to_cart` продолжат работать по текущему каталогу.
7. При недоступном сервере UI покажет ошибку вместо ложного успеха; плохие данные не будут записаны через API.

## Проверка и ограничения

`dotnet build server/SignalStore.Api.csproj`, `npm run build`, `npm test`: браузерный тест проверяет начальные 40 товаров и 50 продаж, фильтры каталога и продаж, создание, редактирование, витрину, продажу, проверку конфликта остатков, удаление и сохранность истории; существующие WebMCP-тесты остаются в наборе. Тесты поднимают оба сервера автоматически; каждый запуск получает новую in-memory SQLite базу с предсказуемыми начальными данными.

Это локальный однопроцессный прототип: база не переживает перезапуск API, нет авторизации, репликации, резервного копирования и постоянных миграций; не выставлять стенд в сеть без отдельной модели доступа и постоянного хранилища. Следующая итерация сможет встроить агента поверх существующего контракта каталога и продаж, отдельно определив доступные ему действия и подтверждение изменений. Текущие WebMCP-инструменты не получают административных прав.
