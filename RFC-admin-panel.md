# RFC: панель управления каталогом, корзинами и заказами Signal Store

## Контекст и задача

В исходном WebMCP-демо каталог из шести товаров был зашит в React-модуль, а оформление заказа не меняло состояние магазина. Для следующей статьи о встроенном агенте нужен существующий рабочий сценарий управления магазином, с которым агент сможет взаимодействовать позднее. Создаём отдельную страницу оператора и один источник данных для витрины, продаж и панели.

## Цели и границы

- На `/admin` показать все товары: название, ID, статус, категорию, цену, физический и доступный остаток, порог низкого остатка; вывести количество товаров и единиц на складе.
- Фильтровать каталог по тексту (включая ID и характеристики), категории, статусу, наличию и диапазону цены; фильтры можно сочетать и сбрасывать. Товары с доступным остатком не выше заданного порога выделяются как товары с низким остатком.
- Создавать и редактировать товары, сохранять их черновиками, публиковать, архивировать и возвращать из архива в продажу. У товара изменяются название, категория, цена, остаток, порог низкого остатка, цвет карточки, метка, описание и характеристики; ID задаётся при создании и остаётся стабильным для корзин и заказов.
- Выполнять массовые действия для выбранных товаров: публиковать, архивировать, менять категорию и остаток.
- Во вкладке «Корзины и заказы» просматривать открытые и брошенные корзины, оформленные, выполненные и отменённые заказы; фильтровать список по товару и статусу. Администратор может выполнить или отменить оформленный заказ.
- На витрине показывать пользовательский раздел «Мои заказы»: созданные из его корзин заказы со статусом, составом и суммой. Пользователь может отменить только оформленный заказ.
- В отчёте за период показывать число выполненных заказов, выручку и показатели по товарам.
- Витрина и WebMCP читают тот же опубликованный каталог; оформление заказа резервирует товар, а успешное выполнение заказа списывает его с физического остатка.
- Сохранить React + Vite и существующие три WebMCP-инструмента. Добавить бэкенд на ASP.NET Core 10 с Entity Framework Core и in-memory SQLite.

Авторизация, платежи, доставка, возвраты, роли, публичное развёртывание и встроенный агент **не входят** в эту итерацию. Корзины и заказы моделируют демонстрационный сценарий, а не реальные покупки. Страница и API без авторизации предназначены только для локального стенда.

## Решение

В dev-режиме Vite обслуживает React SPA и проксирует `/api` на .NET-сервер `127.0.0.1:5080`; `/admin` использует тот же frontend и отдельный экран без смены стека. Прямой доступ к API также ограничен loopback-адресом. Фронтенд запрашивает данные через `src/api.js`, не хранит копию каталога в исходниках. Панель опрашивает API при открытии, витрина загружает каталог при открытии страницы; после изменения или покупки данные повторно запрашиваются. Для просмотра изменений между уже открытыми вкладками требуется обновить страницу.

Хранилище — реляционная SQL-база SQLite в памяти процесса: Entity Framework Core создаёт схему и начальные данные при старте приложения. База существует только пока работает API и при каждом новом запуске создаётся заново, поэтому отдельный файл данных, миграции и настройка пути не нужны. В начальных данных должны быть ровно **40 опубликованных товаров** и **50 выполненных заказов**: каждая позиция заказа ссылается на существующий товар, а физические и зарезервированные остатки после генерации неотрицательны. Генератор должен быть детерминированным, чтобы тесты и демонстрация показывали воспроизводимые данные. Товары физически не удаляются: архивирование меняет статус товара и выводит его из продажи. История заказов остаётся доступной для архивных товаров. Контекст базы живёт в одном процессе API; для демонстрационного локального стенда этого достаточно.

### Статусы и остатки

У товара есть статус `draft`, `published` или `archived`. Черновик виден только в админ-панели; опубликованный товар доступен на витрине, для WebMCP и в новой корзине; архивный товар остаётся в админ-панели и истории, но не продаётся. Публикация переводит черновик или архивный товар в `published`, архивация — любой неархивный товар в `archived`.

Корзина и заказ — одна сущность со статусом: `open_cart` → `submitted` → `completed` или `cancelled`. Корзина в `open_cart`, не изменявшаяся более трёх суток, автоматически получает статус `abandoned` при очередной проверке сервером. Открытая и брошенная корзина не влияет на остатки.

При переводе `open_cart` в `submitted` сервер проверяет доступный остаток и создаёт резерв. Доступный остаток равен физическому `stock` минус `reservedStock`; резерв делает товар недоступным для новой корзины, но не уменьшает физический остаток. При `completed` резерв снимается, а физический остаток уменьшается; при `cancelled` резерв только снимается. Выполнить или отменить можно только заказ в статусе `submitted`; повторные вызовы не меняют остатки. Архивирование не отменяет уже оформленный заказ: его можно завершить или отменить по тем же правилам.

### Контракт API

| Метод и путь | Результат |
| --- | --- |
| `GET /api/products` | Только опубликованные товары, включая товары с нулевым доступным остатком. `?status=all` возвращает также черновики и архивные товары — его использует админ-панель. Фильтрация — на странице. |
| `POST /api/products` | Создать товар в статусе `draft`; `201`, `400` при ошибке данных, `409` при совпадении ID. |
| `PUT /api/products/{id}` | Полностью заменить товар; ID в URL и теле должны совпадать. `200`, `400` или `404`. |
| `POST /api/products/{id}/publish` | Опубликовать черновик либо вернуть архивный товар в продажу; повторный вызов идемпотентен. `200` или `404`. |
| `POST /api/products/{id}/archive` | Архивировать товар, не удаляя запись и историю заказов; повторный вызов идемпотентен. `200` или `404`. |
| `POST /api/products/bulk` | Массово опубликовать или архивировать товары, сменить их категорию либо остаток. Тело содержит ID выбранных товаров и одно действие; операция атомарна. |
| `GET /api/orders?productId={id}&status={status}` | Корзины и заказы от новых к старым. Оба фильтра необязательны и сочетаются; выбор товара включает архивные товары. |
| `GET /api/my-orders` | Заказы для раздела «Мои заказы» на витрине, от новых к старым. В демо без авторизации это те же заказы единственного локального пользователя. |
| `POST /api/carts` | Создать открытую корзину с товарами. Архивные и черновые товары отклоняются. |
| `POST /api/carts/{id}/submit` | Оформить открытую корзину и создать резерв остатков; `200`, `409` при недостаточном остатке или неверном статусе. |
| `POST /api/orders/{id}/complete` | Выполнить оформленный заказ: снять резерв и списать физический остаток. |
| `POST /api/orders/{id}/cancel` | Отменить оформленный заказ и снять резерв. Доступен и администратору, и пользователю со стороны витрины; отменить можно только собственный заказ в статусе `submitted`. |
| `GET /api/reports/sales?from={date}&to={date}` | Сводка по выполненным заказам и товарам за включительный период. |

Модель товара: `id`, `name`, `category`, `price` (целые рубли), `stock` (физические штуки), `reservedStock` (зарезервированные штуки), `lowStockThreshold` (неотрицательное число), `status`, `accent` (HEX), `mark`, `description`, `tags` (массив строк). Сервер проверяет категорию, допустимые диапазоны и формат полей, повторные ID, а также инвариант `0 ≤ reservedStock ≤ stock`. Доступный остаток вычисляется сервером и не передаётся клиентом. Для массового изменения остатка сервер не позволяет установить `stock` ниже уже созданного резерва.

Модель корзины или заказа: `id`, `status`, `createdAt`, `updatedAt`, `items`, `reservedAt` и `completedAt` при наличии. Позиция сохраняет снимок `productId`, названия и цены, количества; поэтому история и отчёты остаются корректными после изменения или архивации товара. У единственного демонстрационного пользователя нет идентификатора и авторизации: «Мои заказы» показывают все созданные на витрине заказы текущего локального стенда. Итоги отчёта включают только заказы `completed`; отменённые, брошенные и открытые корзины в выручку не входят.

## Пользовательские сценарии и критерии приёмки

1. После каждого запуска API в каталоге ровно 40 опубликованных товаров и в истории 50 выполненных заказов; у всех позиций заказов существуют товары, физические и зарезервированные остатки неотрицательны.
2. Открыть `/admin`, найти нужный товар по тексту, сузить список категорией, статусом, наличием и ценой. Увидеть физический, доступный и низкий остаток.
3. Создать товар как черновик: он доступен только в админ-панели. Опубликовать его — товар появляется на витрине. Архивировать опубликованный товар — он остаётся в админ-панели, но исчезает с витрины и не продаётся; публикация архивного товара возвращает его на витрину. Изменения можно применить массово к выбранным товарам: публикация, архивация, категория или остаток.
4. Открытая корзина не меняет остаток. При оформлении корректной корзины появляется заказ `submitted` с резервом; доступный остаток уменьшается, физический — нет. Завершение заказа списывает физический остаток и снимает резерв; отмена снимает только резерв. Недостаточный доступный остаток не создаёт частичный резерв.
5. Открытая корзина, не изменявшаяся больше трёх дней, автоматически отображается как брошенная и не влияет на остаток. В списке корзин и заказов можно отфильтровать записи по товару и статусу; архивный товар остаётся доступным в фильтре и истории.
6. После оформления заказа пользователь видит его в разделе «Мои заказы» с составом, суммой и статусом. Пользователь может отменить собственный заказ `submitted`; резерв освобождается, а заказ получает статус `cancelled`.
7. В отчёте за выбранный период отобразить число выполненных заказов, выручку и данные по товарам; отменённые и незавершённые заказы не входят в итог.
8. Архивированный товар с оформленным заказом не ломает его: администратор может его завершить или отменить. WebMCP `search_products`, `show_product`, `add_to_cart` работают только с опубликованным каталогом.
9. После перезапуска API данные возвращаются к начальному набору. При недоступном сервере UI показывает ошибку вместо ложного успеха; плохие данные не записываются.

## Проверка и ограничения

`dotnet build server/SignalStore.Api.csproj`, `npm run build`, `npm test`: браузерный тест проверяет начальные 40 товаров и 50 выполненных заказов, статусы и массовые действия с товарами, возврат из архива, пороги низкого остатка, фильтры корзин и заказов, резервирование, выполнение, отмену администратором и пользователем, автоматическое определение брошенной корзины, отчёт за период, сохранность истории и инварианты остатков. Существующие WebMCP-тесты остаются в наборе. Тесты поднимают оба сервера автоматически; каждый запуск получает новую in-memory SQLite базу с предсказуемыми начальными данными.

Это локальный однопроцессный прототип: база не переживает перезапуск API, нет авторизации, репликации, резервного копирования и постоянных миграций; не выставлять стенд в сеть без отдельной модели доступа и постоянного хранилища. Следующая итерация сможет встроить агента поверх существующего контракта каталога и продаж, отдельно определив доступные ему действия и подтверждение изменений. Текущие WebMCP-инструменты не получают административных прав.
