# RFC: панель управления каталогом и продажами Signal Store

**Статус:** реализовано в демо · **Ветка:** `feature/admin-catalog-sales`

## Контекст и задача

В исходном WebMCP-демо каталог из шести товаров был зашит в React-модуль, а оформление заказа не меняло состояние магазина. Для следующей статьи о встроенном агенте нужен существующий рабочий сценарий управления магазином, с которым агент сможет взаимодействовать позднее. Создаём отдельную страницу оператора и один источник данных для витрины, продаж и панели.

## Цели и границы

- На `/admin` показать все товары: название, ID, категорию, цену и остаток, а также количество товаров и единиц на складе.
- Фильтровать каталог по тексту (включая ID и характеристики), категории, наличию и диапазону цены; фильтры можно сочетать и сбрасывать.
- Создавать и удалять товары, редактировать их поля: название, категорию, цену, остаток, цвет карточки, метку, описание, характеристики. ID задаётся при создании и остаётся стабильным для корзины и истории.
- Показывать продажи, дату, состав с количеством и ценой на момент продажи, сумму продажи и суммарную выручку.
- Витрина и WebMCP читают тот же каталог; оформление демо-продажи фиксирует заказ и списывает остаток единым действием на сервере.
- Сохранить React + Vite и существующие три WebMCP-инструмента. Добавить бэкенд на ASP.NET Core 8 без новых внешних пакетов.

Авторизация, платежи, доставка, возвраты, роли, публичное развёртывание и встроенный агент **не входят** в эту итерацию. Заказы здесь — записи демонстрационных продаж, а не реальные покупки. Страница и API без авторизации предназначены только для локального стенда.

## Решение

В dev-режиме Vite обслуживает React SPA и проксирует `/api` на .NET-сервер `127.0.0.1:5080`; `/admin` использует тот же frontend и отдельный экран без смены стека. Прямой доступ к API также ограничен loopback-адресом. Фронтенд запрашивает данные через `src/api.js`, не хранит копию каталога в исходниках. Панель опрашивает API при открытии, витрина загружает каталог при открытии страницы; после изменения или покупки данные повторно запрашиваются. Для просмотра изменений между уже открытыми вкладками требуется обновить страницу.

Хранилище — `server/data/store.json` (игнорируется Git). Если файла нет, .NET загружает шесть исходных товаров из `server/seed-products.json`; продажи изначально пусты. Для чистого демо файл можно удалить при остановленном сервере. Путь к хранилищу можно задать через `SIGNAL_STORE_DATA`. Запись сначала идёт во временный файл, затем подменяет основной; операции изменения последовательно выполняются под одним семафором. Для одного локального процесса этого достаточно, внешняя БД для статьи не нужна. История хранит снимок названия и цены: удаление товара из каталога не удаляет прошлые продажи.

### Контракт API

| Метод и путь | Результат |
| --- | --- |
| `GET /api/products` | Весь каталог, включая товары с нулевым остатком. Фильтрация — на странице. |
| `POST /api/products` | Создать товар; `201`, `400` при ошибке данных, `409` при совпадении ID. |
| `PUT /api/products/{id}` | Полностью заменить товар; ID в URL и теле должны совпадать. `200`, `400` или `404`. |
| `DELETE /api/products/{id}` | Удалить из каталога; `204` или `404`. |
| `GET /api/sales` | Продажи от новых к старым. |
| `POST /api/sales` | Тело `{ "items": [{ "productId": "orbit-buds", "quantity": 1 }] }`; `201` со снимком продажи, `400` при неверном запросе, `409` при недостаточном остатке, дубле позиции или отсутствии товара. |

Модель товара: `id`, `name`, `category`, `price` (целые рубли), `stock` (штуки), `accent` (HEX), `mark`, `description`, `tags` (массив строк). Сервер проверяет категорию, допустимые диапазоны и формат полей, повторные ID. Цена и остатки берутся из каталога на сервере; клиент не передаёт их при продаже. Сервер проверяет **все** позиции до списания, поэтому неуспешная продажа не меняет остатки и историю. Продажа имеет `id`, `createdAt` (UTC), `items` со снимком товара и `total`.

## Пользовательские сценарии и критерии приёмки

1. Открыть `/admin`, найти нужный товар по тексту, сузить список категорией, наличием и ценой. Увидеть цену и остаток даже у отсутствующего на складе товара.
2. Добавить товар со всеми полями; он появится на витрине после загрузки страницы и сохранится после перезагрузки. Изменить его цену и остаток — витрина покажет новые значения. Удалить товар — он исчезнет из каталога.
3. Купить на витрине доступный товар: появится запись на вкладке «Продажи» с количеством, суммой и датой, остаток уменьшится. Попытка купить больше доступного вернёт ошибку без частичной записи.
4. Удалить ранее проданный товар: продажа останется видимой с исходной ценой и названием. WebMCP `search_products`, `show_product`, `add_to_cart` продолжат работать по текущему каталогу.
5. При недоступном сервере UI покажет ошибку вместо ложного успеха; плохие данные не будут записаны через API.

## Проверка и ограничения

`dotnet build server/SignalStore.Api.csproj`, `npm run build`, `npm test`: браузерный тест проходит создание, фильтры, редактирование, витрину, продажу, проверку конфликта остатков, удаление и сохранность истории; существующие WebMCP-тесты остаются в наборе. Тесты используют отдельный JSON-файл в игнорируемой `.cache/` и поднимают оба сервера автоматически.

Это локальный однопроцессный прототип: нет блокировки между **разными процессами** API, репликации и механизма миграции JSON-схемы; не выставлять стенд в сеть без отдельной модели доступа и хранилища. Следующая итерация сможет встроить агента поверх существующего контракта каталога и продаж, отдельно определив доступные ему действия и подтверждение изменений. Текущие WebMCP-инструменты не получают административных прав.
